# ADAS LCC Test Lab
### 基于 HighwayEnv 与 pytest 的智能驾驶车道居中控制测试项目

<p align="center">
  <strong>ADAS Testing · Test Automation · Python · HighwayEnv · pytest</strong>
</p>

## 1. 项目简介

本项目是一个面向智能驾驶测试工程岗位的个人实践项目，围绕车道居中控制（Lane Centering Control，LCC）功能，构建从需求分析、测试设计、自动化执行、数据采集、指标判定到缺陷记录和测试证据归档的基础测试流程。

项目使用 Python、HighwayEnv 和 pytest 搭建仿真测试环境。通过构造直线车道横向偏移和正弦曲线车道跟踪场景，验证被测控制器在指定条件下的行为，并将测试结果保存为 CSV、JSON、JUnit XML 和 HTML 等形式。

本项目的重点不是开发或优化一个高性能 LCC 控制算法，而是实践智能驾驶测试工程中的关键工作：

- 将功能需求转化为可执行、可判定的测试用例。
- 根据场景和前置条件执行自动化测试。
- 采集控制器输入、输出及车辆状态数据。
- 根据预先定义的判据进行 PASS / FAIL / ERROR 判定。
- 保留测试执行证据，并将不符合项关联到缺陷记录。
- 区分环境或执行异常与被测功能不满足要求的情况。

> **项目定位：** 基于仿真环境的 ADAS 功能测试学习项目，不代表任何整车企业的内部测试标准，也不替代真实车辆道路测试、硬件在环测试或安全验证。

## 2. 项目背景与测试目标

在智能驾驶测试工作中，测试人员需要理解功能需求、设计场景、执行测试、分析数据，并对发现的问题进行记录和跟踪。

LCC 适合作为入门测试对象，因为它涉及车辆横向位置、航向误差、转向控制输出、车道几何和稳定性等多个可观测量。

本项目围绕以下目标展开：

1. 建立基本的 LCC 测试需求与测试计划。
2. 建立需求、测试用例和测试结果之间的追踪关系。
3. 使用 pytest 实现自动化功能测试。
4. 记录逐周期的控制器输入、控制输出及车辆评价数据。
5. 通过横向误差、车道状态和动作合法性等指标评价测试结果。
6. 输出结构化执行记录和可浏览的测试报告。
7. 根据有效执行证据编写缺陷记录，并明确缺陷当前状态。

## 5. 测试对象与测试范围

### 5.1 被测对象

项目中的 `src/controller.py` 实现了一个简化的学习用途 LCC 控制器。

控制器根据车辆状态和参考状态计算转向动作，并限制输出在环境允许的动作范围内。

测试工程将该控制器视为被测对象（System Under Test，SUT），主要验证其在指定仿真场景下的行为是否满足测试要求，而不是以持续调整参数、追求更优性能为主要目标。

### 5.2 测试范围

| 测试方向 | 主要检查内容 |
|---|---|
| 输入数据有效性 | 控制器观测是否包含必要字段，数据是否有限 |
| 控制输出合法性 | 输出是否有限，是否满足动作空间约束 |
| 直线横向偏移 | 横向误差是否减小，是否达到设定的误差范围 |
| 稳定性检查 | 最终样本及连续尾部样本是否满足误差要求 |
| 曲线车道跟踪 | 曲线路段的最大横向误差及最终稳定性 |
| 车道状态检查 | 是否出现车道外状态 |
| 碰撞状态检查 | 仿真期间是否出现车辆碰撞 |
| 测试证据管理 | 是否生成逐步 CSV、汇总 JSON 和测试报告 |

### 5.3 当前不覆盖的范围

本项目尚不覆盖：

- 真实车辆道路测试。
- 硬件在环（HIL）或车辆在环（VIL）测试。
- 摄像头、毫米波雷达等传感器原始数据测试。
- 感知模型精度与目标跟踪测试。
- 完整的整车级功能安全验证。
- 量产软件的企业内部验收流程。
- 缺陷修复后的正式回归闭环。

## 6. 测试设计与执行流程

本项目按以下测试工程流程开展工作：

### 阶段一：需求分析

明确测试对象、测试目标、输入条件、测量指标及判定标准。

将抽象的功能要求拆分为可检查的测试项，并通过需求追踪文档关联需求和测试用例。

### 阶段二：测试场景设计

为测试场景明确：

- 场景类型和车道几何。
- 初始车辆位置与航向。
- 初始速度。
- 仿真步数与随机种子。
- 环境噪声配置。
- 评价指标及阈值。

正式执行前冻结测试配置和判定标准，避免根据测试结果反向放宽标准。

### 阶段三：自动化执行

通过 pytest 调用测试函数。测试脚本负责创建环境、初始化场景、调用被测控制器、推进仿真并检查运行结果。

执行期间记录控制器输入、控制动作和仿真评价数据。

### 阶段四：数据采集与指标分析

将每个控制周期的数据保存到 CSV，并将汇总指标和判定结果保存到 JSON。

使用逐步数据追溯误差变化，并检查车道状态、碰撞状态和动作合法性。

### 阶段五：结果判定

按预先冻结的判据判断每项要求是否满足。

- **PASS**：所有要求均满足。
- **FAIL**：测试有效完成，但至少一项功能或性能要求不满足。
- **ERROR**：环境或执行脚本异常，导致无法完成有效判定。

环境异常不能直接作为功能缺陷；功能要求不满足也不能因为 pytest 返回非零退出码就简单归类为执行异常。

### 阶段六：报告与缺陷记录

保留原始数据、结构化汇总和测试报告。

对正式测试中发现的不符合项建立缺陷记录，包含需求编号、用例编号、执行编号、预期结果、实际结果、证据路径和当前状态。

## 7. 自动化测试设计

### 7.1 直线车道横向偏移测试

测试通过设置车辆初始横向偏移，观察控制器是否能够降低横向误差。

现有测试包含正、负两个方向的初始偏移，并检查：

- 测试数据是否有效。
- 控制动作是否满足动作空间约束。
- 横向误差是否减小。
- 最终误差是否满足指定范围。
- 是否在规定步数内进入稳定误差带。
- 车辆是否始终保持在车道内。

这组测试用于验证基础横向纠偏行为，并形成初始基线。

### 7.2 曲线车道跟踪测试

曲线测试使用 HighwayEnv 的 `lane-keeping-v0` 环境，并明确选择正弦曲线车道。

测试以固定场景运行 60 步，关闭状态与导数噪声，以便先观察该配置下的基础跟踪表现。

该测试重点检查：

- 最大绝对横向误差。
- 最终横向误差。
- 最后连续 10 个样本的误差。
- 车道内状态与碰撞状态。
- 观测数据及评价数据是否有限。
- 控制输出是否合法。

曲线测试采用独立测试文件 `tests/test_lcc_curve_requirement.py`，与直线测试分开执行和报告，便于定位失败原因。

## 8. 测试结果

### 8.1 直线基线执行

LCC-EXEC-002 的既有执行记录如下：

| 项目 | 结果 |
|---|---:|
| LCC 专项测试 | 18 passed |
| 全套测试 | 19 passed |
| 执行方式 | pytest 自动化测试 |
| 主要场景 | 直线车道横向偏移 |
| 测试范围 | 基础纠偏行为与稳定性检查 |

上述结果只反映当时纳入测试套件的测试项。它不表示曲线用例已通过，也不代表当前仓库所有测试都能通过。

### 8.2 曲线车道正式执行

测试用例：`TC-LCC-CURVE-001`

执行编号：`LCC-EXEC-003`

| 项目 | 冻结标准 | 实际结果 | 判定 |
|---|---:|---:|---|
| 最大绝对横向误差 | ≤ 1.00 m | 2.6398 m | FAIL |
| 最后连续 10 个样本 | 绝对误差均 ≤ 0.25 m | 不满足 | FAIL |
| 车道保持与无碰撞 | 全部在车道内且无碰撞 | 车道外样本 0，碰撞样本 0 | PASS |
| 数据有效与动作合法 | 数据有限、动作满足约束 | 通过 | PASS |

最终判定：**FAIL**。

该结果说明当前冻结版本的控制器在这组曲线仿真配置下未满足横向误差和稳定性要求。

它不证明该控制器在所有速度、道路曲率或噪声条件下都会失败，也不能直接外推到真实车辆道路表现。

### 8.3 环境异常与有效测试结果的区分

曲线用例首次运行时出现环境注册异常：

`NameNotFound: Environment lane-keeping doesn't exist.`

通过导入 `highway_env` 并独立验证环境创建，解决了该问题。首次运行保留为执行异常记录，后续有效执行才用于正式功能判定。

这体现了测试过程中对执行异常和功能不满足的区分。

## 9. 测试证据与归档

本项目使用不同文件格式承担不同的证据管理职责。

| 文件格式 | 主要用途 |
|---|---|

| JSON | 执行元数据、指标汇总、判定结果与失败原因 |

| Console Log | 保留命令执行过程、测试摘要和异常上下文 |

### 9.1 证据目录

- `results/LCC-EXEC-001/`：直线基线测试环境信息与执行报告。
- `results/LCC-EXEC-003/raw_logs/`：曲线测试逐周期 CSV。
- `results/LCC-EXEC-003/run_summaries/`：曲线测试 JSON 汇总。
- `results/LCC-EXEC-003/reports/`：pytest 日志、JUnit XML 和 HTML 报告。

原始数据与汇总报告应保持对应关系。公开证据前应检查执行编号、文件名和测试结果是否一致。

## 12. 运行测试

### 12.1 执行直线专项测试

```bash
python -m pytest -v tests/test_lcc_function.py
```

### 12.2 执行曲线正式用例

```bash
python -m pytest -v tests/test_lcc_curve_requirement.py
```

当前曲线正式用例因既有判据未满足，预期会返回测试失败结果。不要为了获得绿色结果而临时修改阈值。

### 12.3 生成测试报告

```powershell
New-Item -ItemType Directory -Force outputs\manual_run\reports | Out-Null

python -m pytest -v tests/test_lcc_function.py `
    --junitxml=outputs/manual_run/reports/lcc_function_junit.xml `
    --html=outputs/manual_run/reports/lcc_function_report.html `
    --self-contained-html 2>&1 |
    Tee-Object -FilePath outputs/manual_run/reports/lcc_function_console.log
```

说明：此命令是手动执行示例。运行时会生成新的测试结果，实际报告应以本次运行的执行时间和文件内容为准，不应与已归档的历史记录混淆。

## 13. 项目局限与后续方向

当前版本主要验证基础仿真场景中的 LCC 行为与测试流程，存在以下限制：

- 仿真环境与真实车辆的动力学、传感器和执行器行为存在差异。
- 当前曲线测试只覆盖固定的场景配置。
- 项目级误差阈值不代表企业量产验收标准。
- 当前没有真实道路、HIL 或 VIL 证据。
- `BUG-LCC-001` 尚未完成修复验证和回归关闭。
- 探索性实验结果与正式测试结果必须分开标识。

后续可扩展的测试工程方向包括：

1. 增加场景配置与测试数据的统一管理。
2. 建立更完整的需求—用例—执行—缺陷追踪关系。
3. 增加多速度、多初始位置和噪声条件下的场景覆盖。
4. 自动生成缺陷报告和测试执行摘要。
5. 在获得修复版本后实施回归验证。
6. 扩展真实道路测试或 HIL 测试的数据分析流程。

以上是可选的后续方向，不代表这些工作已经完成。

## 14. 个人项目实践重点

本项目重点展示以下测试工程实践：

- 将测试需求转换为明确的检查项和判定标准。
- 使用 Python 与 pytest 实现自动化测试。
- 采集逐周期数据，支持测试结果复核。
- 通过结构化报告保留测试执行证据。
- 区分环境异常与被测功能失败。
- 根据实际测量结果记录缺陷，不以修改阈值掩盖问题。
- 明确当前交付范围与尚未完成的回归工作。
