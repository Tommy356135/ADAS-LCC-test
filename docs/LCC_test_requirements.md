> **边界声明：** 本文档是为学习智驾功能测试流程而建立的工程假设，不是零跑或其他主机厂的内部需求、量产验收规范或安全标准。当前仿真环境没有真实摄像头车道线识别、量产车辆转向执行器、车辆 CAN 通信或完整 ADAS 系统。本项目结论仅适用于本文中记录的代码、配置与仿真条件。

## 1. 目的

将 LCC（Lane Centering Control，车道居中控制）学习项目拆解成可追踪、可执行、可评价的测试需求，为测试方案、测试用例、自动化脚本、缺陷记录和测试报告提供共同依据。

## 2. 被测对象（SUT）与测试环境

- 被测对象：`src/controller.py` 中的 `LCCController` 及 `LCCGains` 参数配置。
- 仿真环境：HighwayEnv `lane-keeping-v0`。
- 控制输入：控制器读取的 `state`、`reference_state` 等约定观测字段，输出一个连续转向动作。
- 环境评测数据：车辆真实位置、车道局部坐标、车道参考航向等，仅用于离线评价，不作为控制器额外输入。
- 当前基线控制参数：`k_lateral=0.025`、`k_heading=0.45`、`max_action=1.0`；参数变体实验归档为探索性数据，不属于正式基线。
- 当前常用执行条件：`SEED=42`、控制步数 60、`state_noise=0.0`、`derivative_noise=0.0`。具体用例可另行定义配置，但必须记录。

## 3. 范围

### 3.1 本轮范围内

1. 环境初始化与执行完整性。
2. 观测与评测数据有效性。
3. 动作空间约束。
4. 初始横向偏差纠正（负偏差与正偏差）。
5. 直线车道中心基线检查。
6. 正弦曲线车道跟踪特性记录。
7. 日志完整性、指标计算、测试状态和报告生成。
8. 回归测试流程与证据归档。

### 3.2 本轮范围外

- 真实摄像头车道线检测与车道边界识别。
- 量产 LCC 算法、EPS/转向执行器和车辆底盘闭环。
- 真实车辆道路测试、HIL/台架测试、CAN/CAN FD 通信验证。
- 多传感器融合、驾驶员监测、人机交互和整车功能安全认证。
- 对生产车辆安全性作出结论。
- 继续优化控制器以追求更小误差；控制器作为固定被测对象，除非新建独立版本并记录变更，否则测试期间不得改动。

## 4. 测试需求

以下 `REQ` 均是学习项目需求，不是产品需求。带阈值的需求在正式执行批次前应评审冻结，执行中不得根据结果反向修改阈值。

| 需求 ID | 需求描述 | 验证方式 | 当前状态 |
|---|---|---|---|
| LCC-REQ-ENV-001 | 环境应能按指定配置创建并重置，且能完成规定仿真步数 | 自动化测试/日志检查 | 已初步验证 |
| LCC-REQ-DATA-001 | 测试记录中的关键数值字段必须为有限数值，且每条记录具有步序号 | 自动化数据校验 | 已初步验证 |
| LCC-REQ-ACT-001 | 每个转向动作必须符合环境动作空间约束 `[-1, 1]` | 自动化断言 | 已初步验证 |
| LCC-REQ-FUNC-001 | 在固定初始偏差 −4.0 m 与 +4.0 m、固定直线路段及无观测噪声条件下，控制器应降低最终绝对横向偏差 | 参数化功能测试 | 已有 14 个测试实例通过；需记录基线版本 |
| LCC-REQ-FUNC-002 | 在 LCC 从车道中心、车道方向对齐的直线路段起步时，系统应维持基线状态且不产生不必要转向 | 直线基线测试 | 已有诊断运行；场景挑战性低，仅作 sanity check，不单独证明弯道能力 |
| LCC-REQ-CURVE-001 | 在正弦曲线车道上，测试应采集横向误差、航向误差、动作与车道状态，用于分析曲线跟踪表现 | 特性/诊断测试 | 已执行一次；当前基线表现退化；正式阈值未批准，暂不作正式 PASS/FAIL |
| LCC-REQ-ROB-001 | 应能够按不同初始偏差、车速、种子和噪声配置执行用例，并保存配置与结果 | 矩阵执行/数据审查 | 已有探索性矩阵；不同车速下按固定步数运行的历史结果不宜直接横向比较 |
| LCC-REQ-REPORT-001 | 每次执行应可追踪到用例 ID、SUT 版本、环境配置、执行状态及输出证据 | 资料审查 | 待补充统一执行记录 |
| LCC-REQ-REG-001 | 测试框架应能对固定用例重新执行，并比较新旧运行结果 | 回归测试/结果对比 | 待正式实现 |
| LCC-REQ-DEFECT-001 | 未满足已冻结判据的结果应形成缺陷/问题记录，并区分控制器问题、测试工具问题、环境问题和无效执行 | 缺陷管理演练 | 待执行 |

## 5. 判定约定

测试状态至少包括：

- **PASS**：执行有效，且全部适用的、预先冻结的判据均满足。
- **FAIL**：执行有效，且至少一项已冻结判据未满足。
- **BLOCKED**：因依赖、环境、资源或前置条件缺失，无法继续执行。
- **INVALID**：执行已发生，但数据/环境/步骤错误使结果无法用于判断。
- **NOT RUN**：尚未执行。
- **CHARACTERIZATION**：仅记录性能特征；尚无已批准的二元验收判据，不将其当作 PASS 或 FAIL。

当前直线偏差纠正测试使用的 `±0.25 m` 最终误差、最晚第 50 步收敛、末 10 个采样保持在误差带内，是**本学习项目的暂定判据**，只适用于对应用例。它们不是量产 LCC 通用标准。曲线测试在曲线验收阈值评审之前应标记为 `CHARACTERIZATION`。

## 6. 需求变更控制

若测试中修改控制器、控制参数、场景配置、采样方法或判定阈值，必须：

1. 生成新版本或配置 ID；
2. 记录变更原因及影响的需求/用例；
3. 保留旧版本与原始结果；
4. 执行受影响用例和必要的回归；
5. 不得覆盖或删除历史基线。
